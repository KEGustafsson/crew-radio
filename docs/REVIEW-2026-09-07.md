## High

### H1 · Replay of recorded packets is possible after a sender goes quiet or a receiver reconnects
`PttEngine.kt:645-652`, `SeqTracker.kt:115-119`, `PttEngine.kt:474-477`, `docs/SECURITY.md:20`.
A node silent for 4 s is dropped and `seqTracker.retain(nodes.keys)` forgets its high-water mark;
the next packet with that (senderId, seq) is admitted as "the first we hear". Both seen-caches are
LRU (4096 ≈ 80 s of one talker) and are wiped on every `disconnect()`. Anyone on the WLAN can
record a member's packets **without the key** and replay them after the member pauses, leaves,
restarts the app (new random id) or after any receiver reconnects: they pass AEAD, the caches, the
rate limit and `admit`, are played, relayed through the mesh, and replayed hellos put a ghost of the
member back on every roster. `SeqTrackerTest.kt:61` asserts this behaviour as intended.
`docs/SECURITY.md:20` claims the opposite.
**Proposed:** (a) stopgap, no wire change: keep per-sender high-water marks in a bounded LRU for the
process lifetime, never clear them or the seen-caches on reconnect, and rewrite SECURITY.md to state
the residual window honestly; (b) proper fix, wire v4: a 32-bit seconds timestamp in the header,
authenticated by the AAD, accepted within ±60 s, with a seen-cache sized for that window.

### H2 · One stalled Bluetooth or Aware peer freezes the mic, the hellos and the LAN relay
`StreamLink.kt:260-266`, `BluetoothTransport.kt:180-188`, `WifiAwareTransport.kt:403-411`,
`PttEngine.kt:566`, `:599-607`. `send()` writes synchronously under `synchronized(output)` on the
caller's thread: the capture thread (every frame), the heartbeat thread (hellos) and every receive
thread that relays. No socket has a write timeout, `soTimeout` or keep-alive. An RFCOMM peer
walking out of range blocks writes until link supervision expires (~20 s); a dead NAN TCP path
blocks once the send buffer fills, for TCP's retransmit horizon. During that time this phone sends
nothing on any transport, drops off every roster, and stops relaying LAN audio.
**Proposed:** a bounded per-link outbound queue (≈16 frames, drop oldest) drained by a
`ptt-bt-tx-*` / `ptt-aware-tx-*` thread; `send()` becomes `offer()`. On Aware also set
`soTimeout` (hellos arrive every second, 5 s is safe) and `keepAlive`, so the reader tears a dead
link down and triggers the redial.

### H3 · The Wi-Fi Aware listener accepts TCP connections from any host on any interface
`WifiAwareTransport.kt:360` `ServerSocket(port)` binds the wildcard address; `:371-372` adds every
accepted socket with no origin check and no cap on links. With `INTERNET` granted, port 47475 is
reachable from the boat or marina WLAN. Content stays protected by AEAD, but every connection
spawns a reader thread and receives a copy of all traffic, and combined with H2 an attacker who
connects and never reads blocks every send on this phone.
**Proposed:** bind to the NAN interface's link-local address (from the responder's
`LinkProperties`), or reject any accepted address that is not an `Inet6Address.isLinkLocalAddress`
on the Aware interface; cap concurrent links (e.g. 16) and drop links that deliver no authenticated
packet within a few seconds.

### H4 · Release signing secrets are visible to every step of the release job, including third-party actions
`.github/workflows/build.yml:75-79` puts the base64 keystore and three passwords in job-level
`env`, so `actions/attest-build-provenance` and `softprops/action-gh-release` (which runs with
`contents: write`) inherit them; the decoded keystore stays at `$RUNNER_TEMP/release.keystore`
for the rest of the job.
**Proposed:** step-level `env` on the two Gradle steps only; `rm -f "$RUNNER_TEMP/release.keystore"`
(`if: always()`) before the attestation and release steps; optionally replace the release action
with `gh release create` so no third-party code runs with the write token.

### H5 · About 120–140 ms of avoidable mouth-to-ear latency
`AudioPlayback.kt:182` sizes the track at 5 frames (≥100 ms) and `Mixer.kt:66-104` writes a frame
every loop whether or not anyone is sending, so in steady state the track is always full: the
"jitter buffer" is a fixed 100 ms delay on top of the mixer's own 40 ms prefill. `OpusEncoder.kt:49`
and `OpusDecoder.kt:232` poll the codec with a zero timeout right after queueing input, so output
usually surfaces on the *next* call, 20 ms later, on both ends.
**Proposed:** track buffer = `minBuf` (or 2 frames) with `PERFORMANCE_MODE_LOW_LATENCY`, showing
`underrunCount` on the Status screen, and grow the mixer prefill instead if underruns appear; poll
once with a ~10 ms timeout after queueing input (or switch the codecs to async callback mode).
Measured on the field phones before/after.

### H6 · A dead AudioRecord or AudioTrack spins an audio-priority thread, silently
`AudioCapture.kt:126-131`: a negative `read()` (`ERROR_DEAD_OBJECT` after an audio-server restart,
or the input stolen by a call) breaks the inner loop and the outer loop spins at
`THREAD_PRIORITY_URGENT_AUDIO`, allocating 640 bytes per iteration, while the UI says
"Transmitting"; under VOX the monitor never keys again. `AudioPlayback.kt:189` ignores `write()`'s
return, so a dead track makes the mixer loop run flat out with no audio and no status line.
**Proposed:** on a negative return stop the loop, report through an `onError` callback, and let the
engine un-key / restart the monitor (re-open after backoff on `ERROR_DEAD_OBJECT`); have the mixer
recreate the track and report once.

### H7 · Signal K plugin: an alarm whose spoken text exceeds 500 characters is never announced
`sk-plugin/lib/bridge.js:109` composes state + path + message and calls `say()`, which throws at
`index.js:211` for texts over `MAX_TEXT`; the catch at `bridge.js:116-119` treats every error as
transient and retries every 5 s forever. The truncation in `FliteTts.normalise` is never reached.
This is the alarm path.
**Proposed:** truncate to `MAX_TEXT` inside `say()` (return `{truncated: true}`), keeping the hard
reject only for the external HTTP/PUT doors if wanted; add a one-off retry timer in the catch that
does not depend on `repeatMs` (with `repeatSec: 0` a failed alarm is currently never retried).

### H8 · Signal K plugin: urgent announcements bypass the queue bound, and synthesis runs before the capacity check
`sk-plugin/lib/queue.js:42-53` returns before the `max` check at `:54` for urgent items, and each
urgent item cancels the one playing; `index.js:213` runs Flite (`await tts.synthesize`) before
`queue.enqueue` at `:218`. Whoever can call `/say` (an admin, any in-process plugin, or anyone on the
WLAN when server security is off) can exhaust memory and CPU. Verified: 999 urgent items queued
past `max = 20`.
**Proposed:** cap urgent items (own small cap or the same `max`), check capacity before
synthesising, and add a per-source token bucket on `say()` (e.g. 10/min) as defence in depth.

## Medium

### Wire, crypto, engine

- **M1 · Wi-Fi Aware PSK is the channel key itself.** `MainActivity.kt:273`,
  `WifiAwareTransport.kt:205,215,291`. The NAN handshake derives its PMK with a WPA-style
  low-iteration PBKDF2 and is capturable in range, so it is a cheaper offline verifier for the
  packet key than the app's own 64 000-iteration KDF; a typed `12345678` is accepted.
  *Proposed:* derive a separate Aware secret, e.g. Base64 of PBKDF2(channelKey, "CrewRadio aware
  v3") (43 printable chars, within 8–63), so the PSK reveals nothing about the packet key; decouple
  `validPassphrase` from the channel key; remove the retired `"crew-radio"` default parameter at
  `WifiAwareTransport.kt:62`. Same-build rule already covers the interop break.
- **M2 · KDF work factor and where it runs.** `ChannelCrypto.kt:55` 64 000 iterations, fixed salt;
  typed keys need only 8 characters with no strength check; derivation runs in a property setter on
  the main thread (`PttEngine.kt:396-402` from `MainActivity.kt:302`). *Proposed:* 600 000
  iterations (OWASP 2023) changed together with `sk-plugin/lib/crypto.js` and the shared vector,
  derived on a worker before `connect`, plus a minimum of 12 characters or a strength warning for
  typed keys. Alternative: keep 64k and require the generated `xxxx-xxxx-xxxx` format.
- **M3 · `startTalking`/`stopTalking` are not mutually excluded.** `PttEngine.kt:491-493`,
  `:539-548`, `:522-535`. Callers: touch handler, MediaSession, Telecom, the monitor thread. Two
  concurrent starts leak an `OpusEncoder` and can run two `AudioCapture`s (every frame sent twice);
  a stop racing a start leaves a capture sending after un-key; `sendFrame` can release the encoder
  twice and broadcast PCM after un-key. *Proposed:* a dedicated `talkLock` around both bodies and
  the encoder swap in `sendFrame` (not the engine monitor: `publishRoster` is `@Synchronized` on it
  and runs on rx threads).
- **M4 · The pre-authentication global bucket lets a keyless WLAN flood starve real traffic.**
  `PttEngine.kt:576`, `RateLimiter.kt:147-148` (400/s, burst 800), charged before dedupe, so both
  WLAN copies of every legitimate frame count. Three full-duplex talkers on WLAN already use
  ~306 pps; ~1000 pps of garbage from anyone on the network (no key needed) drops most authentic
  packets, while AES-GCM on ≤1 KB costs microseconds. *Proposed:* CPU-bound global ceiling
  (≈5000/s) plus a separate bucket charged only when `open()` fails; keep the current order.
- **M5 · A persistent decode error churns MediaCodec instances and leaks.** `PttEngine.kt:730-734`
  removes with `decoders.remove(sender)` (unconditional: can drop a replacement created by another
  thread without releasing it) and does not mark the sender `undecodable`, so the next packet
  creates a new codec, 50 times a second, with a status line each. `undecodable` never expires
  (`:716`, `:770`), so one transient failure mutes a peer for the session. *Proposed:*
  `remove(sender, dec)`, count consecutive failures, mark undecodable after 3 with a 10 s retry.
- **M6 · The heartbeat dies silently on the first exception.** `PttEngine.kt:457-459`: a
  `ScheduledExecutorService` cancels a periodic task that throws; `tick()` reaches `Cipher`,
  `Hello.encode` and every `Transport.send` (BT/Aware catch only `IOException`). This phone then
  drops off every roster while it can still talk. *Proposed:* `try/catch` inside the lambda,
  reporting once.

### Transports

- **M7 · Two Bluetooth links when both phones name each other as peer.** `BluetoothTransport.kt:64`
  always dials and `:72-102` always accepts; no tie-break like Aware's `localId < peerId`.
  Every frame goes out twice (PCM 64 kB/s on RFCOMM), the receiver discards half, and reconnect
  storms double. *Proposed:* on accepting from the device we also dial, keep one link by comparing
  adapter addresses or sender ids; align `docs/ARCHITECTURE.md` ("one link per pair").
- **M8 · `Transport.stop()` blocks the main thread.** `LanTransport.kt:220` `join(500)`,
  `BluetoothTransport.kt:193-198` socket closes, `WifiAwareTransport.kt:416-423`, all called from
  `PttService.disconnect()`/`onDestroy` on the UI thread. *Proposed:* non-blocking stop; do the
  closes on a `ptt-stop` worker; `connect()` waits on a latch only if ordering matters.
- **M9 · Aware `acceptLoop` dies and leaks the listener if `addLink` throws.**
  `WifiAwareTransport.kt:370-373` vs the guarded Bluetooth version at `BluetoothTransport.kt:89-94`.
  `tcpNoDelay`/`getInputStream` throw when the peer resets between accept and setup; the accept
  thread is then gone for the session and the port stays bound. *Proposed:* same try/catch as BT;
  `srv.close()` in a `finally`.
- **M10 · Aware discovery is unauthenticated and per-peer state is unbounded.**
  `WifiAwareTransport.kt:238-245` (any SSI ≥ 4 bytes creates a peer and a `Dial`), `:298`
  (`backoffs` never pruned). Any Aware device publishing `crew_radio` with many low ids makes this
  phone hold a `requestNetwork` per id (20 s timeout each; `ConnectivityManager` throws past 100
  outstanding requests, after which real peers cannot get one). On API 29 there is no
  `onServiceLost` (the comment says 11+), so a departed peer is redialled forever. *Proposed:*
  cap concurrent dials (≈8), prune `backoffs`/`peers`, expire peers not rediscovered on API 29,
  and put an HMAC of the id under the channel key in the SSI so foreign publishers are ignored.
- **M11 · LAN: interface choice and the Wi-Fi callback can disagree, and `rejoin()` never skips the wait.**
  `LanTransport.kt:229-235` enumerates (any `wlan*`), `:71-82` keys on the `TRANSPORT_WIFI`
  network; on the hotspot-hosting phone (`swlan0`/`ap0`) or with two Wi-Fi interfaces, events from
  the other interface close a working socket. `:184-194`: `pause()` calls `drainPermits()` before
  waiting, discarding the permit `rejoin()` just released, so every Wi-Fi change still waits the
  full first backoff. *Proposed:* drive the socket from the callback's `Network`/`LinkProperties`
  and ignore other networks; replace the drain-then-wait with a "rejoin requested" flag.
- **M12 · Bluetooth adapter off at Connect is permanent for the session, and the hello still advertises BT.**
  `BluetoothTransport.kt:58-61` returns without `running = true`; `PttEngine.kt:658` sets the BT
  flag from membership in `transports`. LAN and Aware both wait and recover. *Proposed:* watch
  `BluetoothAdapter.ACTION_STATE_CHANGED` and start on `STATE_ON`; derive the hello flag from
  "has a listener or a link".
- **M13 · Aware: a link that lands after its `Dial` finished is orphaned.**
  `WifiAwareTransport.kt:318-328` checks `finished` before `addLink`, `:381-401` assigns
  `dial.link` later; `onLost`/`onUnavailable` in between leaves a live link nobody redials when it
  drops, with no status line. *Proposed:* check `finished` inside `addLink`'s `lifecycle` block and
  close the socket instead of registering it.

### Audio

- **M14 · VOX has no talk time-out.** `MicGate.kt:38-41` closes only after 75 consecutive frames
  below `closeRms`; steady wind or engine noise above 40 RMS on a boom keeps the mic keyed
  indefinitely, and in half duplex blocks reception. *Proposed:* a 60 s gate time-out in
  `voiceFrame` with a status line, and/or an adaptive noise floor.
- **M15 · A stream that paused replays its next burst without a prefill.** `Mixer.kt:110-125`:
  `primed` is set once and never cleared, so after a pause under 1 s the first frame of the next
  phrase plays immediately and any jitter is concealed at every word onset. *Proposed:* reset
  `primed`/`concealed` in the `return null` branch at `:120`.
- **M16 · Unbounded 700 ms heal loop when a Bluetooth device is listed but refused.**
  `AudioRoute.kt:84-87`, `:196-205`: the refusal branch calls `clearCommunicationDevice()`, which
  notifies the listener, which calls `heal()`, which re-runs `apply()`; `retries` caps only the
  other path. Each pass reaches `syncMonitor()`. *Proposed:* count heals like retries; skip the
  clear when the current device is already not the headset.
- **M17 · Capture start/stop, codec release and route changes run on the caller's thread.**
  `PttEngine.kt:240`, `:251` (join up to 500 ms), `:508`, `:543-545` from the touch handler and the
  main handler; `AudioRoute.kt:77` runs `getDevices()`/`setCommunicationDevice` on the sensor
  thread. Opening an AudioRecord is 50–200 ms on many HALs: visible jank on every key. *Proposed:*
  a single-thread `ptt-audio-ctl` executor owning the talk/monitor state machine.
- **M18 · Decimator passband droop.** `Decimator.kt:161-172`, 25 taps for factor 3: −1.9 dB at
  6 kHz, −5 dB at 7 kHz, only −10.7 dB at the new Nyquist. Harmless for aliasing (Opus at 16 kHz is
  wideband-capped) but dulls sibilants. *Proposed:* `16*factor+1` taps, cutoff 0.48/factor; add a
  6 kHz passband and 9 kHz alias test (the current test uses 24 kHz, which any low-pass nulls).

### App, platform, usability, enterprise

- **M19 · The talk-key buzz never fires: `VIBRATE` is not declared.** `PttService.kt:285-288`
  catches the `SecurityException` and does nothing; `README.md:85` promises a short buzz on key and
  a double buzz on un-key. Lint reports it. *Proposed:* declare `android.permission.VIBRATE`
  (normal permission). Also declare `ACCESS_NETWORK_STATE` for `registerNetworkCallback`
  (`LanTransport.kt:94`, Lint error; API contract even where the platform is lenient).
- **M20 · No runtime-permission result handling; permanent denial is silent.**
  `MainActivity.kt:235` asks on every launch, bundling mic, notifications and BT scan;
  `:185` after "don't ask again" the switch snaps back with no message; no
  `onRequestPermissionsResult`/`registerForActivityResult` exists, so after granting the user must
  tap again. *Proposed:* `RequestMultiplePermissions` contract; continue the connect on grant; on
  permanent denial a one-line message with a Settings button; ask for BT/Aware only when the tile
  is tapped and for notifications on first Connect.
- **M21 · TalkBack users cannot talk in half duplex.** `MainActivity.kt:116` suppresses
  `ClickableViewAccessibility`; the disc keys only on raw `ACTION_DOWN/UP` (`:207-225`) and the
  click listener acts only in full duplex (`:226-233`). Tiles and head count are colour-only
  (`activity_main.xml:92-126`, `contentDescription="@null"`), and the channel row plus its switch
  are two focus targets for one action. *Proposed:* treat `performClick` as a latch toggle when
  touch exploration is on (or a custom `AccessibilityAction`), `announceForAccessibility` on state
  changes, `stateDescription` on tiles, "N aboard" on the count.
- **M22 · `targetSdk 34` and the concrete cost of moving.** `app/build.gradle.kts:42`. Play and
  managed Google Play require API 35 (36 from August 2026), so an enterprise fleet cannot be served
  from Play as-is. Verified impact of 35/36: edge-to-edge is enforced (`activity_main.xml:8` uses
  plain padding; `themes.xml:15-16,32-33` bar colours are ignored) so the header sits under the
  status bar and the disc under the gesture bar; `screenOrientation="portrait"`
  (`AndroidManifest.xml:46`) is ignored on large screens at 36; predictive back is safe (no
  `onBackPressed`); FGS timeouts do not apply to microphone/connectedDevice; no native code.
  *Proposed:* window-insets handling in the three activities, then `targetSdk = 36`. A decision,
  not a bug; sideloading works without it.
- **M23 · Channel key handling: at rest, on screen and on the keyboard.** No
  `dataExtractionRules` (`AndroidManifest.xml:38` has only `allowBackup="false"`; on API 31+
  device-to-device transfer is governed by the rules file), so whether the key follows a phone
  migration is implicit. `preferences.xml:18-22` shows the full key as the settings summary and
  gives it the default text keyboard (autocorrect, suggestions, capitalisation: "q7wk-…" becomes
  "Q7wk-…"). No share/copy/QR affordance; `README.md:199` says "no data worth losing" while
  `README.md:35-37` explains that the key is what every phone needs. *Proposed:* rules excluding
  `sharedpref` from cloud backup and device transfer (documented in SECURITY.md); masked summary
  with a reveal; `TYPE_TEXT_VARIATION_VISIBLE_PASSWORD | TYPE_TEXT_FLAG_NO_SUGGESTIONS`; a
  "Share key" action; fix the README sentence; optionally wrap the value with an AndroidKeyStore key.
- **M24 · README claims a greyed-out Aware tile that does not exist.** `README.md:51`; no
  `FEATURE_WIFI_AWARE` check anywhere; the only signal is a status line after Connect that the main
  screen does not show. *Proposed:* grey the tile on `!hasSystemFeature(FEATURE_WIFI_AWARE)`; on
  API < 33 also check `LocationManager.isLocationEnabled` (Aware discovery silently finds nobody
  with location services off) and say so.
- **M25 · Enterprise gaps.** No managed configuration (`APP_RESTRICTIONS` meta-data,
  `RestrictionsManager`): an EMM cannot provision key, group, port, hops or name. All UI text is
  English and mostly outside `strings.xml` (`preferences.xml`, `arrays.xml`, `SettingsActivity.kt:36-43`,
  `StatusActivity.kt:99-158`, `PttService.kt:124,143,282`, manifest `label="Settings"`,
  `CallService.kt` "Crew Radio"); `uppercase()` without a locale. Version mismatch across the crew
  is invisible (the hello carries no build number; no update check). The foreground notification is
  not marked `FOREGROUND_SERVICE_IMMEDIATE`, so Android 12+ may defer it up to 10 s while
  `README.md:58` tells the user to read it right after joining. *Proposed:* `app_restrictions.xml`
  with restriction values taking precedence in `Prefs`; move strings to resources (mechanical) before
  any translation; add `versionCode` to the hello (hello v2) and an "OLD BUILD" mark on the roster;
  set the immediate flag.

### Build, CI, supply chain

- **M26 · Nothing verifies what the build downloads.** No `gradle/verification-metadata.xml`; no
  `distributionSha256Sum` in `gradle-wrapper.properties`; the wrapper jar is the 8.14.x one (never
  regenerated at the 9.7 bump), so wrapper-side fixes since 8.14 are missing. *Proposed:*
  `./gradlew wrapper --gradle-version 9.7.1 --gradle-distribution-sha256-sum acd53f1edaf02f1a8ff99879f8a34b302661a057d9b063ae9e35b552f804d20a`
  (re-check the sum before committing), then `--write-verification-metadata sha256` and commit,
  with a documented regeneration step for Dependabot PRs.
- **M27 · Stale repository name breaks the documented attestation check.** `build.yml:144`,
  `README.md:44`, `sk-plugin/package.json:10,13,15`, `sk-plugin/README.md:67,69`,
  `sk-plugin/docs/capture_admin_ui.md` say `KEGustafsson/android-push-to-talk`; the remote is
  `KEGustafsson/crew-radio`. `gh attestation verify --repo` matches the certificate's source
  repository exactly, so the published command fails. *Proposed:* replace all references.
- **M28 · CI shape.** `build.yml:24-26` `cancel-in-progress: true` also applies to `main`, so two
  merges within ~10 min cancel the first release (a versionCode with no Release or attestation).
  `codeql.yml:35` scans `java-kotlin` only: the plugin (the code most exposed to untrusted input)
  and the workflows are unscanned while `docs/SECURITY.md:63` says "CodeQL on every change".
  Only the APK is attested; the SBOM and `.sha256` are not. Lint is not run. *Proposed:*
  `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`; add `javascript-typescript`
  (`build-mode: none`) and `actions` to CodeQL; attest all three files; add `lintRelease` with
  `abortOnError` to the build job once the six errors are fixed.
- **M29 · Silent debug-key fallback when `CREWRADIO_KEYSTORE` is set but unusable.**
  `app/build.gradle.kts:27-28,60`: a typo in the path or a missing password degrades to the debug
  key with no message (CI's apksigner check catches it there, a local build does not), and also
  disables the shallow-clone guard. *Proposed:* throw when the variable is set explicitly and the
  file or password is missing; print which key signs the release build.

### Signal K plugin

- **M30 · Routes are registered without `router.access(...)`.** `index.js:169,170,183`. On
  current servers unregistered plugin routes require admin, so a readonly/readwrite user opening the
  webapp gets 401 on every `/status` poll; with security off, `/say` is open to the WLAN with no
  rate limit. *Proposed:* `router.access("readonly")` for `/status`, `"readwrite"` for `/say`
  (fall back to `router` on older servers); token bucket on `say()` (see H8).
- **M31 · Flite runs synchronously on the server's main thread.** `lib/tts.js:321`
  `wasi.start(instance)`: measured 63 ms stall per sentence on x86, "about a second on a Pi" per
  the README; the whole Signal K server pauses, and the plugin's own 20 ms frame timer stalls so the
  phones' mixers run dry mid-announcement (lead is 100 ms). `pbkdf2Sync` also blocks at start.
  *Proposed:* run Flite in a `worker_threads` Worker.
- **M32 · Body parsing.** `index.js:177-181`: Express 4 sets `req.body = {}` for an unparsed
  content type, so the documented plain-text `POST /say` reaches `say({})` and fails; over 10 000
  characters the request is destroyed without a 413; any body starting with `{` is parsed as JSON
  regardless of content type (a `text/plain` cross-site form can reach it, mitigated by the cookie's
  SameSite default). *Proposed:* treat an empty object as "no body" / check `req.is("text/*")`;
  answer 413 before destroying; require `application/json` for the JSON path.
- **M33 · No sequence tracking; a replayed hello re-points the unicast copies.** `lib/node.js:143`
  (4096-entry FIFO seen-cache, ~80 s of one talker), `:346` learns `n.address` from any direct
  packet, `nodes` is uncapped (the app caps at 64). A captured, replayed authentic packet marks the
  node talking (holding announcements up to `waitForSilenceMs`) and redirects unicast copies to the
  replayer. *Proposed:* per-sender wrap-aware high-water marks like the app's `SeqTracker`, cap
  `nodes`, update the address only when the sequence advances.

## What is done well

The wire design is tight and its ordering is right (global bucket, AEAD, seen look, sender bucket,
seen write, with the reasons written next to the code); AAD really is the header with only the ttl
byte zeroed and `hops` is bound, with a test proving both directions; parsing of packets and hellos
is strict; `open()` never throws; nonces and keys come from `SecureRandom` with an unbiased
alphabet. Every blocking call sits on a named `ptt-*` thread through `transportThread`, which turns
`SecurityException` into a status line instead of a crash; each transport has one `lifecycle`
monitor ordering "add a link" against `stop()`; `Backoff` is pure and tested and used everywhere a
loop waits; the `Dial` object is a clean answer to NetworkCallback double-teardown. The codec
plumbing supplies all three Opus csd buffers and reads the real output rate; concealment is designed
around the real MediaCodec limitation; the mixer's hot loop is allocation-free and mute-before-cue is
exactly as documented; VOX thresholds are measured, not guessed. The manifest earns every
permission, both services are correctly scoped, the foreground-service path is right for targetSdk
34, `allowBackup` is off. The workflows are least-privilege, every action is SHA-pinned with a
version comment, checkouts do not persist credentials, the release job fails closed on missing
secrets and on a certificate mismatch, and the git history is clean. The plugin mirrors the app
byte for byte with a shared vector, escapes every server string on its page, masks the key, and is
covered at 98.5 % with the real WASM engine exercised. `SECURITY.md`, `docs/SECURITY.md` and the
README are concrete and, with the exceptions listed above, accurate.
